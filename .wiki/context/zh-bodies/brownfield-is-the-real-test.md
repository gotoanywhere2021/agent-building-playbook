## 这是什么（What it is）

绿地（greenfield）工作在恭维一个智能体系统。一个全新原型没有遗留约束、没有要保留的生产行为、没有隐藏依赖、没有埋在代码里的组织记忆，错了也没有风险——这正是为什么一场光鲜的绿地演示，几乎证明不了一个工作流能否真正把活干完。棕地（brownfield）才是智能体成熟度的真正考验，因为棕地是所有这些压力同时在场的地方：真实用户依赖的运行系统、无人记录却人人依赖的行为、只在坏掉时才浮现的依赖、以事故计价的失败成本。令人鼓舞的发现是：智能体在棕地确实能派上用场，而且往往比预期的更有用，因为棕地环境里富含的恰恰是智能体擅长消费与产出的那些工件：它们能分析既有行为、从代码的现状生成用户故事、在任何重写之前建立回归测试、产出兼容层、并排运行新旧实现以比较输出、生成迁移计划、翻查日志与事故历史找出要紧的行为、并在保留行为的同时重写组件。危险用法与成熟用法之间的界线是清晰的。危险的版本是盲目的重写——把智能体指向旧系统、要一个新的、然后祈祷。成熟的版本从验收证据出发，先问那个承重的问题：重写之后什么必须仍然为真？它刻画既有行为、用回归测试把行为钉死，然后才动实现——于是『它还能工作』是一句经过核查的断言，而不是一句祈祷。

## 适用场景（When to reach for it）

- 修改或替换任何真实用户已经依赖的系统时——把保留当前行为当作首要要求，而不是事后考量。
- 你被一次干净重写诱惑时——先投入刻画并钉死既有系统实际做什么，然后在那些测试的保护下改动它。
- 既有系统的行为没有文档时——在动它之前，让智能体从代码、日志与事故历史生成用户故事、回归测试与行为描述。
- 评估一个智能体工作流是否真正成熟时——用带真实约束的棕地任务测试它，而不是一场把所有难点都藏起来的绿地演示。
- 在两个实现之间迁移时——并排运行新旧实现并 diff 其输出，让分歧作为数据被捕获，而不是作为事故被发现。

## 慎用场景（When NOT to）

- 真正的抛弃式原型，没有要保留的既有行为、没有生产风险——棕地纪律是无物可保护时的纯开销。
- 已知既有行为是错的、明确目标就是要改变它——这时保留它才是 bug 而不是要求；钉住你打算保留的行为，而不是你打算修复的那些。
- 刻画无法进行、因为遗留系统完全无法被运行或观察时——把风险上报给人，而不是让智能体在虚假的覆盖感之下盲改。

## 实例（Exemplars）

- Michael Feathers — https://www.informit.com/store/working-effectively-with-legacy-code-9780131177055 — Working Effectively with Legacy Code：在改动之前围绕既有行为放置刻画测试（characterization test）的奠基性纪律——本模式交给智能体的正是这项人类实践
- Jimenez et al., "SWE-bench: Can Language Models Resolve Real-World GitHub Issues?" (arXiv:2310.06770) — https://arxiv.org/abs/2310.06770 — 实证支持：真实仓库评测显示，在玩具基准上表现良好的模型只能解决约 2% 的真实棕地 GitHub issue，确认绿地能力不能迁移到遗留代码库

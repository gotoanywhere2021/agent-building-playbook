## 这是什么（What it is）

仓库看起来像存储——文件居住的地方——但在智能体工作流中，它发挥着工作记忆与上下文边界的作用。仓库之内是智能体可以看到、搜索与推理的内容；仓库之外，从实用角度看是不可见的。这让仓库形态成为一个在两个方向上都有尖锐取舍的上下文工程决策。仓库太大——一个智能体可以触达一切的庞大单体仓库（mono-repo）——就会毒化上下文：智能体检回不相关的文件，混淆不相关的事务，把注意力预算烧在噪声上。仓库太窄——一个排除了必要依赖、共享 schema 或解释某条惯例的文档的紧切片——智能体就会挨饿，凭空幻觉出它够不到的信息。因此单体仓库与窄仓库之争不只是组织架构或构建系统问题；它是一个关于智能体在给定类别的工作中应当在工作记忆里持有什么的问题。仓库边界由此成为系统认知架构（cognitive architecture）的一部分，与任何架构一样，它应当被刻意选择、按工作定尺寸、并在工作改变时修订——而不是偶然继承自代码碰巧被拆分的方式。

## 适用场景（When to reach for it）

- 当智能体不断拉入不相关文件或混淆事务时——仓库太宽、正在毒化上下文；收窄边界。
- 当智能体反复幻觉出恰好活在仓库之外的事实时——它在挨饿；放宽边界或把依赖带进来。
- 设计新的智能体工作流时：把仓库边界当作设计的一部分来决定，就像你决定提示词里放什么一样。
- 在为智能体驱动的工作选择单体仓库还是拆分仓库时——把它当作上下文工程决策，而不仅仅是构建或所有权决策。
- 当工作本身的形态改变时——重新审视边界，因为对一类任务正确的上下文边界对另一类是错的。

## 慎用场景（When NOT to）

- 当主要消费者是人类而非智能体，且仓库布局为运转良好的人类工作流而优化时。
- 当重塑仓库对构建、所有权或工具链的破坏超过它对智能体的帮助时——用检索或子仓库视图修复上下文范围，而不是物理上重新拆分。
- 当智能体的上下文问题其实是披着仓库外衣的提示词或检索问题——先诊断，再重组文件系统。

## 实例（Exemplars）

- Chatlatanagulchai et al., "Agent READMEs: An Empirical Study of Context Files for Agentic Coding"（arXiv:2511.12884）— https://arxiv.org/abs/2511.12884 — 实证支持：发现仓库级上下文文件（AGENTS.md、CLAUDE.md）是开发者为塑造智能体认知而精心维护的复杂演化工件——证明仓库结构发挥着持久认知基础设施的功能
- Xu et al., "Everything is Context: Agentic File System Abstraction for Context Engineering"（arXiv:2512.05470）— https://arxiv.org/abs/2512.05470 — 形式化：提出一种 Unix 风格的文件系统抽象，其中目录组织即上下文管理架构，把文件布局视为受治理的智能体认知基础设施

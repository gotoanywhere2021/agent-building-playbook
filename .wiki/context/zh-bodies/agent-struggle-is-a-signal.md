## 这是什么（What it is）

代码库一旦变得纠缠不清，智能体在其上的表现就会退化——而这种退化是一支可用的仪表，不只是令人沮丧。当智能体更新了若干重复调用点（call site）中的一个、却悄悄漏掉其余的；当它为把一次变更完整握住而耗尽上下文；当它在测试仍然红着时宣布完工；当它坚称失败是『符合预期』、随后又自相矛盾——这些都不是随机的模型失误；它们是代码矿井里的金丝雀（canary in the code mine）。让代码对智能体困难的那些性质——重复、低内聚、应当一起变更的东西散落各处、迫使一次性加载过多上下文的复杂度——同样是让人类困难的性质。因此，与其把智能体的吃力当作对抗它的理由或归咎于模型的理由，不如把它当作代码质量正在滑落的早期预警信号，并据此行动：让智能体审阅代码、点名可维护性问题、规划一次重构；审阅并引导这份计划；如果智能体自己无法把代码清理得足够好，就用称手的重构工具完成结构性重构。这一做法把一件恼人之事重新框定为反馈。一个过去一次搞定、如今突然要试三次的智能体，正在告诉你关于代码的某件事，而廉价的应对是去听。

## 适用场景（When to reach for it）

- 一个过去能把代码库处理得很好的智能体开始乱撞、卡顿或需要多次尝试——把它表现的变化当作诊断信号，而不只是运气不好。
- 看到经典征兆——变更只落在一份重复副本上而漏了同侪、测试仍在失败时报告『我完成了』、对什么能用的说法自相矛盾——把它们读作重复与复杂度的坏味道（smell）。
- 想把一个在更干净代码库上本可胜任的任务归咎于模型时——换工具之前，先检查代码。
- 作为常备习惯：像盯着构建时长或事故率那样，把智能体的费力程度当作可维护性的先行指标来观察。

## 慎用场景（When NOT to）

- 吃力确实是模型的能力局限，或只是干净代码上的硬任务时——并非每次失败都是代码坏味道；先确认信号，再下令重构。
- 真正的修复是一条有针对性的提示词（prompt）或一段缺失的上下文、而非结构性问题时——不要因为一条指令说得不够具体，就去重构能正常工作的代码。
- 还负担不起重构时——照样记录信号；不要让『现在没法重构』悄悄变成『信号是噪音』。

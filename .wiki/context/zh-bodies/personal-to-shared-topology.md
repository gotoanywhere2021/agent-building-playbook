## 这是什么（What it is）

个人实践者借 agent 变得极其高效，演化出个人工作流——自己的提示词、工具、会话习惯和引导直觉——产生出色的局部结果。但个人的聪明不会自动组合成团队运营模型。十几个人各自运行私有、未成文的工作流，不是一个与 agent 协作良好的组织；而是十几座孤岛，其做法无法被评审、移交、治理或共同改进。更糟的是，agent 默认局部优化，最好的局部答案可能悄悄违反组织的战略、政策或共享品味——对某位工程师的任务最优的工作流，可能与整个系统需要去的方向相互拉扯。解法是在个人效能之上刻意构建组织拓扑（topology）：共享产物（规范、计划、决策、日志）让工作在人与人之间可携带；共享评审规范让质量成为团队属性而非个人习惯；共享可观测性让组织能看到它的 agent 在做什么、花多少；共享模式库让某人发现的有用操作手法连同其失败模式一起对所有人可用。目的不是抹平个人巧思，而是让它可组合——把私人杠杆变成一个对齐的运营模型。

## 适用场景（When to reach for it）

- 当多个人各自在与 agent 的孤立协作中变得高效，而他们的做法无法被集体评审、移交或改进。
- 当一个局部最优的 agent 工作流持续产出偏离团队战略、政策或共享品味的结果。
- 当有价值的操作手法只存在于个人头脑或私人配置中——把它们捕获为带有使用指引和失败模式的共享模式。
- 当入职缓慢，因为没有共享运营模型可交给新人，只有一堆散落的个人工作流。
- 当组织无法跨人看到其 agent 在做什么、花多少——投资共享可观测性与评审规范。

## 慎用场景（When NOT to）

- 不要过早标准化；在早期探索阶段，让个人工作流先分叉、先证明自己，再固化成共享规范。
- 避免把个人效能官僚化成扼杀巧思的合规开销——那正是你想组合起来的东西。
- 这不是要求每项做法完全相同；目标是对齐与可携带，不是为了统一而统一。
- 在工作真正是某个人孤立、低风险的领域、无物可组合时，不要强加共享拓扑。

## 实例（Exemplars）

- Mel Conway, "How Do Committees Invent?" (Datamation, 1968) — http://www.melconway.com/Home/Committees_Paper.html — 经典先例：论证系统映照其组织的沟通结构；『逆康威操作（inverse Conway maneuver）』——刻意重构团队拓扑以得到期望的系统形态——是康威定律（Conway's Law）后来的实践者延伸（并非出自 1968 年那篇论文），它为本模式在个人效能之上构建共享产物与评审规范的主张提供了根基。

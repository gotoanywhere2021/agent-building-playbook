## 这是什么（What it is）

规范（specification）与实现一旦分离就会开始漂移。实现之前写下的规范是愿景；实现一旦开始，若不随之更新，规范就成了负资产。当某个 agent（或人）读到一份过时的规范并据此展开工作，产出就会以累积的方式偏离现实——建立在错误地基上的每一层工作都会成倍放大返工成本。让规范保持同步，意味着把规范更新视为实现任务的一部分，而不是可以推迟的文档清理工作。规范是系统*应当*做什么的事实来源；代码是系统*实际*在做什么的证据。两者都必须保持最新。

漂移还有第二个更隐蔽的来源：意图本身不是静止的。随着利益相关者对具体产物的反应，他们对自身需求的理解也在变化，因此项目初期写得很干净的规范到项目中段可能已经错了——不是因为谁犯了错，而是因为目标移动了。如果工作流让规范忠实于*最初*的意图，而*实际*意图已经改变，那就是在针对一个死掉的产物做优化。补救办法是设置明确的**意图刷新点（intent refresh points）**——在这些时刻对照组织当前想要的重新检查规范：

- 原型评审之后；
- 用户测试之后；
- 发现了改变可行性判断的技术约束之后；
- 监管或合规解读之后；
- 生产环境反馈之后；
- 一份重要的 bug 报告暴露了错误假设之后；
- 模型生成了意料之外却比要求更好的东西之后。

目标不是无休止的折腾——这些检查点中的大多数都会确认规范仍然正确。目标是确保当意图真正移动时，规范随之移动，而不是让团队忠实奔向一个已无人想要的目标。

## 适用场景（When to reach for it）

- 每当实现揭示出某个被规定的行为是错误的、含糊的或不可能的——先更新规范再写修复，而不是之后。
- 增加或移除功能时：规范变更与代码变更必须在同一个提交（commit）中交付。
- 给 agent 一份规范让其工作时——交付之前先核对规范是否反映了代码库的当前状态。
- 评审已完成的工作时：不仅检查代码，还要检查规范是否准确反映了实际构建的内容。
- 任何改变公共接口、文件路径或模块边界的重构之后。

## 慎用场景（When NOT to）

- 明确限定为探索性质、终将删除的一次性（spike）实现——为不会活过探索期的工作花时间更新规范，浪费的是学习预算。
- 早期头脑风暴阶段，规范明确是草稿且所有读者都知道它不具权威性——但要清晰地标注出这一点。

## 实例（Exemplars）

- 多 agent 分歧最常见的来源，是某个子 agent 拿着协调者（orchestrator）已作废的规范版本在工作。同步纪律可以完全杜绝这一类失败。
- Amplifier 的 TASKS.md 约定把任务文件视为活文档，由 agent 随任务推进而更新——同样的同步原则应用于项目管理。
- Gojko Adzic, *Specification by Example* (2011) — https://gojko.net/books/specification-by-example/ — 形式化：以与实现保持同步的活文档作为规范，由自动化测试充当唯一权威参考；2012 年 Jolt 奖获奖作品。
- Cyrille Martraire, *Living Documentation* (2019) — https://www.pearson.com/en-ca/subject-catalog/p/living-documentation-continuous-knowledge-sharing-by-design/P200000009531/9780134689364 — 形式化：将活文档从可执行测试扩展到所有知识产物；展示自动化的对账机制如何防止整个代码库内的规范漂移。
- 2389 Research, documentation-audit — https://github.com/2389-research/documentation-audit — 一方实践（first-party）：对照代码库现实验证文档——刻意『猎捕』漂移（『抓到文档里的谎言』），而不是等着下一个基于过时规范工作的读者去发现。
